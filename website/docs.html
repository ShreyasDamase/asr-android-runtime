Connection overview

ASR Android Runtime manages phone sensors and lets you enable two independent data paths. Pick the one that matches the tool you want to receive the data.

01 / SOURCE

Android Runtime

Reads enabled sensors and publishes their available data.

02 / TRANSPORT

DDS or TCP

DDS carries ROS 2 topics; TCP carries ASR telemetry to Studio.

03 / DESTINATION

Robot or Studio

A ROS 2 subscriber receives topics, or Studio visualizes telemetry.

Choose the connection path for the receiving application.
PathDestinationNetwork setup
ROS 2 DDSROS 2 node, robot, or host subscriberWi-Fi network or Android USB tethering
Studio TCPASR Studio desktop applicationWi-Fi, or USB with ADB reverse

These paths are separate. ASR Studio is a TCP diagnostics client, not a DDS bridge. ADB reverse forwards Studio's TCP connection; it does not turn on USB-tether DDS.

ROS 2 and DDS

ROS 2 uses DDS-based middleware for its publish/subscribe communication. In ASR, the Android Runtime participates in the ROS 2 graph and publishes enabled sensor data as topics. A ROS 2 subscriber or robot node can discover and receive those topics without routing them through ASR Studio.

Topics use a device-specific namespace such as /asr_android_168. The device ID varies. These are examples from the runtime; topic availability depends on the phone hardware, permissions, and enabled modules.

Examples of Android Runtime ROS 2 topics.
Topic suffixROS 2 message typeNotes
imusensor_msgs/msg/ImuInertial and orientation data, when available.
gpssensor_msgs/msg/NavSatFixLocation requires permission and a usable location source.
batterysensor_msgs/msg/BatteryStateBattery state updates.
camera/image/compressedsensor_msgs/msg/CompressedImageCompressed camera frames, when supported and enabled.
statusstd_msgs/msg/StringRuntime status heartbeat.

The primary Android flavor uses Cyclone DDS; a Fast DDS comparison flavor is also available. The documented and tested host setup uses ROS 2 Lyrical with rmw_fastrtps_cpp. Both sides must use the same ROS_DOMAIN_ID (default 0) and be able to discover each other on the selected network. This describes the tested setup, not guaranteed interoperability for every middleware, network, or ROS 2 distribution.

Start the Android Runtime, enable the matching DDS transport, and enable the sensors you need. A publisher may show that it is waiting for discovery until another ROS 2 participant is present on the network.

Wi-Fi DDS

  1. Connect the phone and ROS 2 host or robot to the same reachable Wi-Fi network. The network must permit peer DDS discovery.
  2. Configure the same ROS_DOMAIN_ID on the phone and host; the default is 0. Use rmw_fastrtps_cpp for the documented host configuration.
  3. Start the phone runtime, enable Wi-Fi DDS, and enable the desired sensor modules.
  4. Use ros2 topic list to inspect discovered topics. To confirm messages, echo a topic such as /asr_android_168/imu, replacing 168 with the device ID shown by the runtime.

The ASR USB Link Monitor is not needed for Wi-Fi DDS. It is a USB-only diagnostic; Wi-Fi can be checked with an ordinary ROS 2 subscriber or the robot's existing node.

USB-tether DDS

USB DDS uses Android's USB tethering to create an IP network path between the phone and host. DDS discovery and topic traffic then travel over that network interface. It is not a USB serial or UART transport.

  1. Connect the phone to the ROS 2 host and enable USB tethering in Android system settings.
  2. Start the phone runtime and enable USB DDS. For an isolated check, leave Wi-Fi DDS disabled.
  3. On the host, use the same ROS domain and the documented rmw_fastrtps_cpp setup. A subscriber or robot node can receive the topics.
  4. Optionally run the ASR ROS 2 USB Link Monitor for persistent USB discovery and sensor-flow diagnostics: 
    ros2 launch asr_ros2 connect.launch.py transport:=usb

The monitor is optional and USB-only; it reports graph visibility separately from received sensor callbacks. If automatic interface selection is ambiguous, the monitor supports an explicit interface argument. See the USB Link Monitor guide for setup and diagnostics.

TCP to ASR Studio

ASR Studio connects directly to the phone over TCP and displays camera, sensor, audio, and runtime telemetry. The default port is 4242. This connection is independent of ROS 2 DDS; enabling TCP does not enable ROS 2 publishing.

Wi-Fi TCP

  1. Connect the phone and computer to the same reachable network.
  2. In ASR Studio, open Devices, choose Wi-Fi, enter the computer's local IP address, then choose Listen (Server).
  3. In the Android app's TCP section, enable the connection and enter the computer IP address with port 4242.

What Studio does—and does not do

Studio decodes ASR's TCP telemetry for live diagnostics and visualization. It does not join the ROS 2 graph as a DDS subscriber and does not forward or bridge DDS topics. For ROS 2 data, connect a ROS 2 subscriber or robot node directly to the phone's DDS participant.

For installers and complete Studio setup details, visit the ASR Studio overview.

USB / ADB TCP

For Studio over USB, Android Debug Bridge (ADB) can reverse-forward the Studio TCP port. The phone's TCP client then connects to its own loopback address, and ADB carries that connection to Studio on the computer.

  1. Connect the phone over USB, enable USB debugging, and authorize the computer.
  2. In Studio, open Devices, select USB / ADB, and choose Auto-Configure USB / ADB (1-Click Setup). Studio runs: 
    adb reverse tcp:4242 tcp:4242
  3. Choose Listen (Server) in Studio.
  4. Enable TCP in the Android app and use host 127.0.0.1 and port 4242.

ADB reverse is not USB tethering. It forwards a TCP port for Studio. To use ROS 2 DDS over USB, enable Android USB tethering and the app's USB DDS transport separately.

Troubleshooting

No ROS 2 peer or topics appear

  • Confirm the Android Runtime is running, the intended DDS toggle is on, and the needed sensor modules are enabled.
  • Check that phone and host use the same ROS_DOMAIN_ID and that the host uses the documented rmw_fastrtps_cpp configuration.
  • Check the selected Wi-Fi or USB-tether interface and whether the network or firewall allows peer discovery.
  • For USB diagnostics, check the Link Monitor's interface selection and distinguish a visible topic from actual message callbacks.

Studio does not connect

  • Make sure Studio is listening on port 4242 before enabling the phone's TCP connection.
  • For Wi-Fi, verify the phone can reach the computer's local IP and that the entered address and port are correct.
  • For USB / ADB, confirm the device is authorized and the reverse rule is configured; the phone should connect to 127.0.0.1:4242.
  • Remember that Studio TCP and ROS 2 DDS are independent; enabling one does not start the other.

For Android installation, complete topic definitions, and build details, consult the Android Runtime README. Recorded backend tests and known limits are in the DDS backend comparison.

Network note: The current TCP telemetry path does not use TLS, and the inspected DDS configurations do not enable DDS Security. Use trusted networks and destinations. See the Privacy Policy for more information.
